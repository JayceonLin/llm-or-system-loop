怎麼做出一個用到 LLM 的 OR 系統

    作業研究（OR）系統是幫人做決策的程式：把排產、配送、選址這類問題寫成數學模型，再算出最好的做法。

    加入大型語言模型（LLM）之後，系統可以自己讀懂文字、寫出模型與程式。

    教材來源：本專案的 Wiki，整理自來源論文與自製範例

    • 說出怎麼評估一個系統，以及做這種系統的限制與設計建議

    先備知識：模型有三個部分，交給求解器來算

    決策變數：你能決定的量，例如每天做幾杯紅茶。

    目標函數：想讓它越大或越小越好的式子，例如利潤。

    限制式：不能違反的條件，例如茶葉每天只有這麼多。

    • 求解器：專門解最佳化模型的軟體，例如 Gurobi。它保證算出最好的答案，或告訴你這題無解。
    • 線性規劃（LP）：目標函數和限制式都是一次式，變數可以是小數。
    • 混合整數規劃：在線性規劃上，再規定某些變數只能是整數。

    第 4 站：錯了就帶著錯誤訊息重寫，但只修得了小錯

    驗證回圈就是重複「試、檢查、再改」。

    漏掉限制式、語法錯誤修得好；一開始就想錯的模型修不了

    OptiMUS

    LLM 自己產生單元測試（自動檢查結果的小程式，自製術語表），把執行錯誤與沒通過的測試交回 LLM 修正。

    Chain-of-Experts

    評估器（不是 LLM）執行程式與測試案例；錯了用反向反思，把專家倒過來逐一檢查。

    OptiGuide

    Safeguard 檢查 LLM 產生的程式，觸發自我除錯，或停下來回報錯誤。

    其他極限：GPT-3.5 自動產生的測試常常誤導；改寫或除錯一兩次後，效果就不太再提升。

    多代理人：讓好幾個代理人各負責一件事

    代理人是會自己決定下一步、使用工具的 AI 程式。

    誰決定下一步：OptiMUS 照固定流程，Chain-of-Experts 由 LLM（指揮者）決定

    OptiMUS：一個代理人寫模型、寫程式、執行、測試、修正。

    Chain-of-Experts 的分工

    LLM程式檢查未註明

    1. 指揮者依序挑專家
    2. 專家留下意見
    3. 彙整器合成最後答案
    4. 評估器執行程式與測試

    代價：

    • 意見多了，會超過 LLM 的上下文長度（一次能讀進來的文字上限，自製術語表）。
    • 步驟越多，推理時間與 API 呼叫越多（程式透過網路請 LLM 服務做一次工作，自製術語表）。

    最佳化器另一條路：OPRO 讓 LLM 直接提出解，看分數再改進

    元提示：提示裡放問題描述，與之前的解和分數

    LLM未註明

    1. LLM 依元提示產生新解，每步最多 8 個
    2. 計算新解的分數
    3. 把新解與分數放回元提示

    OPRO 從 20 個城市開始，就輸給專門的方法（最遠插入法）

    旅行推銷員問題（拜訪每個城市一次、總路程最短）和最佳解的差距，越小越好

    10 個城市：OPRO（gpt-4）0.0%

    10 個城市：最遠插入法3.2%

    50 個城市：OPRO（gpt-4）11.0%

    50 個城市：最遠插入法9.8%

    主要用途是最佳化提示詞；作者說它不是要贏過求解器，大問題也放不進提示。

    另一條研究路線：訓練 LLM 本身更會建模

    前面五站都在「怎麼用」LLM，這條研究路線是讓 LLM 本身更會建模

    資料合成：自動產生更多「題目＋模型」的練習資料

    監督式微調：用這些資料再訓練 LLM

    對齊：讓模型的輸出更符合偏好

    綜述是整理整個領域方法、資料集與未來方向的論文。它以統一方式重測，微調過的 ORLM-LLaMA-3 8B 在 IndustryOR 得到 42.9%、在 ComplexLP 得到 59.5%（兩份都是評估用的考卷），在較難的資料集上勝過 Chain-of-Experts。

    評估：考卷不一定可靠，數字不能直接比

    54.0%

    IndustryOR 的錯誤率至少有這麼多

    • 基準資料集是大家共用的考卷。綜述請 11 位專家重新檢查：NL4Opt 錯誤率至少 26.4%；除了 EasyLP，每份都超過 15%
    • 錯誤來源：題目有邏輯漏洞、參數定義不清、標準答案本身是錯的
    • 比目標值：只比最佳值；模型錯了也可能剛好算出相同的值
    • 比模型：比較模型的係數，或算相似分數
    • Chain-of-Experts 的準確率：原論文用 GPT-4，基礎題 LPWP 64.2%、複雜題 ComplexOR 31.4%；綜述改用 GPT-4o 重測，EasyLP 94.4%

    限制與設計建議：計算交給求解器，驗證交給程式

    限制

    • 模型可能一開始就想錯；題目越複雜，正確率越低
    • 把公司資料直接交給 LLM 有外流風險；OptiGuide 讓資料留在求解器與資料庫

    設計建議

    • 計算交給求解器，不讓 LLM 心算
    • 驗證交給不是 LLM 的程式；錯了要帶著錯誤訊息重做
    • 設定重試上限、能停下來回報、保留人的判斷，並用可靠的題目評估

    做這份簡報的流程也照這些建議設計：產生者和驗證者分開、每一步都有重做次數上限、關鍵處停下來給人確認。

    小測驗：計算、驗證與評估

    先想一想，再點題目看答案。

    Q1　LLM 寫好程式之後，為什麼真正的計算要交給求解器？

    LLM 擅長讀懂文字，求解器擅長精確計算；LLM 會算錯。

    Q2　驗證回圈修得好哪種錯、修不了哪種錯？

    漏掉限制式、語法錯誤修得好；一開始就想錯的模型修不了。

    Q3　兩篇論文的準確率，可以直接拿來比誰比較強嗎？

    不行。用的 LLM 不同、考卷不同，數字不能直接比。

    總結：做 LLM × OR 系統的五個重點

    • 系統拆成五站：問題輸入、建模、寫程式交給求解器、驗證與修正、解釋結果與 what-if。
    • LLM 擅長讀懂文字，負責寫模型與程式；計算交給求解器，不讓 LLM 心算。
    • 驗證回圈只修得了小錯，一開始就想錯的模型修不了。
    • 驗證交給不是 LLM 的程式，設定重試上限、能停下來回報，保留人的判斷。
    • 設計時先決定 LLM 當翻譯者、最佳化器還是解說員；評估時先確認考卷可不可靠，數字不能直接比。
