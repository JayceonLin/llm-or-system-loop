怎麼做出一個用到 LLM 的 OR 系統

    作業研究（OR）系統是幫人做決策的程式：把排產、配送、選址這類問題寫成數學模型，再算出最好的做法。

    加入大型語言模型（LLM）之後，系統可以自己讀懂文字、寫出模型與程式。

    教材來源：本專案的 Wiki，整理自來源論文與自製範例

    先備知識：模型有三個部分，交給求解器來算

    決策變數：你能決定的量，例如每天做幾杯紅茶。

    目標函數：想讓它越大或越小越好的式子，例如利潤。

    限制式：不能違反的條件，例如茶葉每天只有這麼多。

    • 求解器：專門解最佳化模型的軟體，例如 Gurobi。它保證算出最好的答案，或告訴你這題無解。
    • 線性規劃（LP）：目標函數和限制式都是一次式，變數可以是小數。
    • 混合整數規劃：在線性規劃上，再規定某些變數只能是整數。

    第 1 站：把文字題整理成有結構的資料

    NL4Opt 競賽

    • 在題目裡標出 6 種元素：變數、參數（題目給的數字）、目標方向、目標名稱、限制方向、限制上限
    • 這一項的第一名，F1 分數是 0.939；F1 同時考慮「標得準」和「沒漏標」，越接近 1 越好

    OptiMUS

    • 使用者填一份有 6 個欄位的 SNOP，數值資料另存成 JSON 檔（用「名稱：值」存資料的文字格式，自製術語表）
    • 好處：很長的數據表不用塞進提示；代價：不能直接用一般文字輸入

    這就是抽象模型：參數先用符號表示，數據之後再給；具體模型則把數值直接寫在題目裡。

    NL4Opt

    先產生意義表示，也就是邏輯形式的中間表示，再轉成求解器能讀的格式。

    方法準確率
    建模第一名 UIUC-NLP0.899
    ChatGPT（gpt-3.5-turbo）合併任務0.927

    版本差異：依表格數字，ChatGPT 比第一名高 2.8 個百分點；論文討論段寫的是高 2 個百分點。

    OptiMUS

    讓 LLM 寫出變數、限制式與目標。

    輸出是給人和下一站都看得懂的模型文件。

    Chain-of-Experts

    把建模拆給好幾位專家：

    • 術語解釋
    • 各部分擷取
    • 建模知識補充
    • 建模專家：寫出完整的數學模型，通常是混合整數規劃

    第 3 站：LLM 寫程式，真正的計算交給求解器

    系統LLM 寫什麼
    OptiMUS用 Gurobi 或 cvxpy 寫 Python 程式
    Chain-of-ExpertsLP 格式檔（求解器可以直接讀的模型文字檔，自製術語表）與 Gurobi 程式
    OptiGuideCoder 把問題、背景與範例組成提示，讓 LLM 寫程式
    • 為什麼分工：LLM 擅長讀懂文字，求解器擅長精確計算
    • LLM 會算錯，也會重複產生以前的解
    • 讓 LLM 直接找解的 OPRO，問題變大後就輸給專門的方法

    成本：OptiMUS 成功的執行，不含求解器時間，每次都在 7 分鐘內完成；平均用掉 4117.1 ± 1509.7 個 token（LLM 讀寫文字時的計算單位，用得越多，通常花的時間與費用也越多，自製術語表）。

    第 4 站：錯了就帶著錯誤訊息重寫，但只修得了小錯

    • OptiMUS：LLM 自己產生單元測試（一小段自動檢查的程式，自製術語表），把執行錯誤與沒通過的測試交回 LLM 修正
    • Chain-of-Experts：評估器執行程式與測試案例，它不是 LLM；錯了用反向反思，把專家倒過來逐一檢查
    • OptiGuide：Safeguard 檢查 LLM 產生的程式，觸發自我除錯，或停下來回報錯誤
    • 漏掉限制式、語法錯誤修得好；一開始就想錯的模型修不了
    • 用 GPT-3.5 時，自動產生的測試常常誤導；多做一兩次改寫或除錯後，效果就不太再提升

    第 5 站：把結果翻成白話，回答 what-if 問題

    例如：某個需求改向供應商 B，成本會怎麼變？

    1. 使用者用文字問 what-if
    2. Coder 組成提示，LLM 寫程式
    3. Safeguard 檢查後交給求解器或資料庫
    4. Interpreter 讀取紀錄，寫成人看得懂的回答

    組提示、寫程式、檢查與執行這幾步可以重複，直到結果令人滿意。

    情況GPT-4 準確率
    沒有給範例59%
    同類型題目，給 5 或 10 個範例92–93%
    不同類型題目，給 10 個範例84%（隨機挑）、80%（挑最相近的）

    實際部署：用在 Azure 的伺服器供應鏈；以前回答一個 what-if 問題，需要超過 3 位作業人員加上 1 位待命工程師。

    依據 Wiki：05-explain-and-whatif

    多代理人：讓好幾個代理人各負責一件事

    代理人是會自己決定下一步、使用工具的 AI 程式。

    OptiMUS

    一個代理人照固定流程做：寫模型、寫程式、執行、測試、修正。

    Chain-of-Experts

    • 指揮者：一個 LLM，決定下一步請哪位專家
    • 彙整器：把各專家的意見合成最後答案
    • 評估器：不是 LLM，執行程式與測試案例，把結果轉成回饋

    Chain-of-Experts 的代價：

    • 專家意見多了，會超過上下文長度（LLM 一次能讀進來的文字上限，自製術語表）
    • 步驟越多，推理時間與 API 呼叫（程式透過網路請 LLM 服務做一次工作，自製術語表）越多
    依據 Wiki：multi-agent glossary

    LLM 的三種角色：翻譯者、最佳化器、解說員

    翻譯者：把文字題變成模型與程式，交給求解器算。

    第 1～3 站｜NL4Opt、OptiMUS、Chain-of-Experts

    最佳化器：不寫模型，自己提出解，看分數再改進。

    不走五站｜OPRO

    解說員：模型已經有了，幫不會寫程式的人問 what-if，再翻成白話。

    第 3～5 站｜OptiGuide

    • 新問題、要從頭建模：用翻譯者。
    • 只能評分的問題：可以考慮最佳化器，但它在大問題上有限制。
    • 公司已經有模型：用解說員。

    三種角色都有「試、檢查、再改」的回圈。

    這個分法是本 Wiki 的整理，不是某一篇論文提出的。

    依據 Wiki：llm-roles

    最佳化器另一條路：OPRO 讓 LLM 直接提出解，看分數再改進

    提示裡放問題描述，以及之前產生過的解和分數，這就是元提示。

    1. LLM 根據元提示產生新的解，每一步最多 8 個
    2. 計算新解的分數
    3. 把新解與分數加進元提示，進入下一輪
    • 旅行推銷員問題：拜訪每個城市一次、總路程最短
    • OPRO（gpt-4）和最佳解的差距：10 個城市 0.0%、50 個城市 11.0%；從 20 個城市開始，專門的方法（最遠插入法）比較好
    • 最主要的用途是最佳化提示詞；作者說它不是要贏過專門的求解器，大問題也放不進提示
    依據 Wiki：llm-as-optimizer 03-code-and-solver

    另一條研究路線：訓練 LLM 本身更會建模

    資料合成：自動產生更多「題目＋模型」的練習資料。

    監督式微調：用這些資料再訓練 LLM。

    對齊：讓模型的輸出更符合偏好。

    綜述（整理整個領域的方法、資料集與未來方向的論文）以統一方式重測：微調過的 ORLM-LLaMA-3 8B 在 IndustryOR 得到 42.9%、在 ComplexLP 得到 59.5%（兩份都是評估用的考卷），在較難的資料集上勝過 Chain-of-Experts。

    還沒解決：長的推理過程很難標註；針對最佳化建模的訓練技術研究還不夠。

    評估：考卷不一定可靠，數字不能直接比

    54.0%

    IndustryOR 的錯誤率至少有這麼多

    • 基準資料集是大家共用的考卷。綜述請 11 位專家重新檢查：NL4Opt 錯誤率至少 26.4%；除了 EasyLP，每份都超過 15%
    • 錯誤來源：題目有邏輯漏洞、參數定義不清、標準答案本身是錯的

    • 比模型：比較模型的係數，或算相似分數

    限制與設計建議：計算交給求解器，驗證交給程式

    限制

    • 模型可能一開始就想錯；題目越複雜，正確率越低
    • 把公司資料直接交給 LLM 有外流風險；OptiGuide 讓資料留在求解器與資料庫

    設計建議

    • 計算交給求解器，不讓 LLM 心算
    • 驗證交給不是 LLM 的程式；錯了要帶著錯誤訊息重做
    • 設定重試上限、能停下來回報、保留人的判斷，並用可靠的題目評估

    做這份簡報的流程也照這些建議設計：產生者和驗證者分開、每一步都有重做次數上限、關鍵處停下來給人確認。

    小測驗：計算、驗證與評估

    先想一想，再點題目看答案。

    Q1　LLM 寫好程式之後，為什麼真正的計算要交給求解器？

    LLM 擅長讀懂文字，求解器擅長精確計算；LLM 會算錯。

    Q2　驗證回圈修得好哪種錯、修不了哪種錯？

    漏掉限制式、語法錯誤修得好；一開始就想錯的模型修不了。

    Q3　兩篇論文的準確率，可以直接拿來比誰比較強嗎？

    不行。用的 LLM 不同、考卷不同，數字不能直接比。

    總結：做 LLM × OR 系統的五個重點

    • 系統拆成五站：問題輸入、建模、寫程式交給求解器、驗證與修正、解釋結果與 what-if。
    • LLM 擅長讀懂文字，負責寫模型與程式；計算交給求解器，不讓 LLM 心算。
    • 驗證回圈只修得了小錯，一開始就想錯的模型修不了。
    • 驗證交給不是 LLM 的程式，設定重試上限、能停下來回報，保留人的判斷。
    • 設計時先決定 LLM 當翻譯者、最佳化器還是解說員；評估時先確認考卷可不可靠，數字不能直接比。
