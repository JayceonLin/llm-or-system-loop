# 重點清單

## K01 OR 系統把決策問題寫成數學模型；用到 LLM 的 OR 系統可以拆成五站 {wiki=overview.md}
- **作業研究**（OR）系統把排產、配送、選址這類問題寫成數學模型，再算出最好的做法；過去寫模型需要專家，Gurobi 的使用者有 81% 具研究所學歷。
- 加入 LLM 後，系統可以自己讀懂文字、寫出模型與程式，再交給求解器計算。
- 五站依序是：問題輸入 → 建模 → 寫程式交給求解器 → 驗證與修正 → 解釋結果與 what-if。

## K02 新手術語表（自製）：先認識模型種類、檔案格式與 LLM 用量的幾個詞 {wiki=topics/glossary.md}
- 這些是自製的白話解釋，不是來自來源論文。**線性規劃**（LP）是目標函數和限制式都是一次式的模型，變數可以是小數，手搖飲範例就是一個；**混合整數規劃** 再規定某些變數只能是整數。
- **LP 格式檔** 是求解器可以直接讀的模型文字檔；**JSON** 是用「名稱：值」存資料的文字格式；**單元測試** 是一小段自動檢查的程式，確認某個結果符合預期。
- **token** 是 LLM 讀寫文字時的計算單位；**API 呼叫** 是程式透過網路請 LLM 服務做一次工作；**上下文長度** 是 LLM 一次能讀進來的文字上限。token 與 API 呼叫越多，通常花的時間與費用也越多。

## K03 自製範例：手搖飲店要決定紅茶與奶茶每天各做幾杯 {wiki=examples/tea-shop.md}
- 自製題目：紅茶每杯利潤 20 元、奶茶每杯 30 元；每杯都用 10 公克茶葉，每天最多 5,000 公克；奶茶每杯另要 150 毫升鮮奶，每天最多 30,000 毫升。
- 第 1 站標出變數、目標方向、參數與限制；第 2 站寫成模型：x₁ = 紅茶杯數，x₂ = 奶茶杯數，最大化 20x₁ + 30x₂，限制 10x₁ + 10x₂ ≤ 5000、150x₂ ≤ 30000、x₁, x₂ ≥ 0。

## K04 自製範例：求解器算出答案，what-if 只要改一個數字重算 {wiki=examples/tea-shop.md}
- 自製結果：每天做紅茶 300 杯、奶茶 200 杯，利潤 12,000 元；第 4 站把答案代回去，茶葉和鮮奶都剛好用完。
- what-if：茶葉每天多進到 6,000 公克，紅茶變成 400 杯、奶茶仍是 200 杯，利潤變成 14,000 元。
- 範例程式用 PuLP 3.3.2 實際執行過。

## K05 第 1 站：在題目文字裡標出 6 種元素（NL4Opt） {wiki=system/01-problem-input.md}
- 6 種元素是：變數（我們能決定的量）、參數（題目給的數字，例如每杯利潤）、目標方向（要越大越好還是越小越好）、目標名稱（想最佳化的東西，例如利潤）、限制方向（不超過、至少、等於）、限制上限（限制裡的那個數字）。
- 這個子任務第一名的 **F1** 分數是 0.939，基準模型是 0.906；F1 同時考慮「標得準」和「沒漏標」，越接近 1 越好。

## K06 第 1 站的另一種做法：要求結構化輸入，資料另外放（OptiMUS） {wiki=system/01-problem-input.md}
- OptiMUS 要求使用者填一份有 6 個欄位的 **SNOP**，數值資料另存成 JSON 檔，只把資料的格式交給 LLM。
- 好處是很長的數據表不用塞進提示；代價是不能直接用一般文字輸入。
- 這就是 **抽象模型**：參數先用符號表示，數據之後再給；**具體模型** 則把數值直接寫在題目裡。

## K07 第 2 站：最佳化模型有三個部分 {wiki=system/02-modeling.md}
- **決策變數**：我們能決定的量，例如每天做幾杯紅茶。
- **目標函數**：想讓它越大或越小越好的式子，例如利潤。
- **限制式**：不能違反的條件，例如茶葉每天只有這麼多。

## K08 第 2 站：NL4Opt 先寫成中間表示，ChatGPT 的準確率超過比賽第一名 {wiki=system/02-modeling.md}
- 根據第 1 站標出的元素，產生邏輯形式的「意義表示」，再轉成求解器能讀的格式。
- 準確率：基準模型（BART）0.610、比賽第一名 UIUC-NLP 0.899、ChatGPT（gpt-3.5-turbo）合併任務 0.927。
- 版本差異：依表格數字，ChatGPT 比第一名高 2.8 個百分點；論文討論段寫的是高 2 個百分點。

## K09 第 2 站：讓 LLM 直接寫模型，或讓好幾位專家分工 {wiki=system/02-modeling.md}
- OptiMUS 讓 LLM 用 Markdown 寫出變數、限制式與目標。
- Chain-of-Experts 把建模拆給術語解釋、各部分擷取、建模知識補充、建模專家等好幾位專家；建模專家寫出完整的數學模型，通常是混合整數規劃。

## K10 第 3 站：LLM 寫程式，真正的計算交給求解器 {wiki=system/03-code-and-solver.md}
- **求解器** 是專門解最佳化模型的軟體，例如 Gurobi；它保證算出最好的答案，或告訴你這題無解。
- OptiMUS 用 Gurobi 或 cvxpy 寫 Python 程式；Chain-of-Experts 寫求解器讀的 LP 格式檔與 Gurobi 程式；OptiGuide 的 Coder 組好提示讓 LLM 寫程式。
- 為什麼這樣分工：LLM 擅長讀懂文字，求解器擅長精確計算；LLM 會算錯，也會重複產生以前的解，直接找解的 OPRO 在問題變大後就輸給專門的方法。

## K11 第 3 站的成本：OptiMUS 成功的執行，不含求解器時間，每次都在 7 分鐘內完成 {wiki=system/03-code-and-solver.md topics/glossary.md}
- 成功的執行平均用掉 4117.1 ± 1509.7 個 token。
- **token** 是 LLM 讀寫文字時的計算單位，用得越多，通常花的時間與費用也越多；這句白話解釋出自自製的術語表。

## K12 第 4 站：執行、檢查，錯了就帶著錯誤訊息重寫 {wiki=system/04-verify-and-repair.md}
- OptiMUS：LLM 自己產生 **單元測試**，檢查輸出格式、限制是否滿足、結果是否自相矛盾；把執行錯誤與沒通過的測試回饋給 LLM 修正，也會把題目換句話說多跑幾次，任一版本成功就算解出。
- Chain-of-Experts：評估器（不是 LLM）執行程式與測試案例，錯了就用 **反向反思** 把專家倒過來逐一檢查。
- OptiGuide：**Safeguard** 檢查 LLM 產生的程式，觸發自我除錯，或停下來回報錯誤。

## K13 第 4 站的極限：驗證回圈只修得了小錯，模型寫錯是最難修的錯 {wiki=system/04-verify-and-repair.md system/02-modeling.md}
- 漏掉限制式、語法錯誤修得好；一開始就想錯的模型修不了，一旦卡在錯誤的解空間，再多試幾次也很少有用。
- 用 GPT-3.5 時，自動產生的測試常常誤導，反而降低表現；多做一兩次改寫或除錯後，效果就不太再提升。

## K14 第 5 站：把結果翻成白話，回答 what-if 問題（OptiGuide） {wiki=system/05-explain-and-whatif.md}
- what-if 問題的例子：如果某個需求改向供應商 B 而不是供應商 A 進貨，成本會怎麼變。
- 流程：使用者用一般文字發問 → **Coder** 組成提示 → LLM 寫程式 → Safeguard 檢查後交給求解器或資料庫 → **Interpreter** 寫成人看得懂的回答。
- 綜述把「可解釋性」與「人機協作」列為未來方向。

## K15 第 5 站的成效：給範例後準確率明顯提高，並已實際部署 {wiki=system/05-explain-and-whatif.md}
- GPT-4 準確率：沒有給範例 59%；同類型題目給 5 或 10 個範例 92–93%；不同類型題目給 10 個範例 84%（隨機挑）、80%（挑最相近的）。
- 用在 Azure 的伺服器供應鏈；以前回答一個 what-if 問題，需要超過 3 位作業人員加上 1 位待命工程師。

## K16 LLM 在系統裡的三種角色：翻譯者、最佳化器、解說員 {wiki=topics/llm-roles.md}
- **翻譯者** 把文字題變成模型與程式（第 1～3 站）；**最佳化器** 自己提出解、看分數再改進（不走五站）；**解說員** 幫不會寫程式的人問 what-if 再翻成白話（第 3～5 站）。
- 設計時先決定角色：新問題要從頭建模用翻譯者；只能評分的問題可以考慮最佳化器，但它在大問題上有限制；公司已經有模型用解說員。
- 這個分法是本 Wiki 的整理，不是某一篇論文提出的。

## K17 多代理人：讓好幾個代理人各負責一件事 {wiki=topics/multi-agent.md}
- **代理人** 是會自己決定下一步、使用工具的 AI 程式；OptiMUS 照固定流程做，Chain-of-Experts 由 **指揮者** 決定下一步請哪位專家。
- **彙整器** 把各專家的意見合成最後答案；**評估器** 不是 LLM，負責執行程式與測試案例，把結果轉成回饋。

## K18 另一條路：OPRO 讓 LLM 直接提出解，看分數再改進 {wiki=topics/llm-as-optimizer.md}
- **元提示** 裡放問題描述與之前的解和分數；LLM 每一步最多產生 8 個新解，算分後放回提示，進入下一輪。
- 旅行推銷員問題（拜訪每個城市一次、總路程最短）中，OPRO（gpt-4）和最佳解的差距：10 個城市 0.0%、50 個城市 11.0%；從 20 個城市開始，最遠插入法比較好。
- 最主要的用途是最佳化提示詞；作者說它不是要贏過專門的求解器，大問題也放不進提示。

## K19 評估：常用的考卷本身不一定可靠 {wiki=topics/evaluation.md}
- **基準資料集** 是大家共用的考卷；綜述請 11 位專家重新檢查，每一題至少 3 人交叉確認。
- 錯誤率至少有：NL4Opt 26.4%、IndustryOR 54.0%；除了 EasyLP，每個資料集的錯誤率都超過 15%；錯誤來源包括題目敘述有邏輯漏洞、參數定義不清、標準答案本身是錯的。
- 取自教科書的題目可能早就在 LLM 的訓練資料中，OptiGuide 因此自己寫題目。

## K20 評估：判斷答案對錯有兩種方式 {wiki=topics/evaluation.md}
- **比目標值**：只比較求解器算出的最佳值和標準答案；缺點是模型錯了也可能剛好算出相同的值。
- **比模型**：比較模型的係數，或算出 0 到 1 的相似分數。

## K21 評估：同一個系統換了 LLM 或考卷，數字就差很多 {wiki=topics/evaluation.md}
- Chain-of-Experts 在原論文用 GPT-4：基礎題 LPWP 64.2%、複雜題 ComplexOR 31.4%；綜述改用 GPT-4o 重測：EasyLP 94.4%。
- 基礎模型不同、考卷不同，數字不能直接比。
- 評估自己的系統時，先確認考卷可不可靠，再說明用的是哪個 LLM、哪份考卷。

## K22 系統比較：沒有一個系統五站全包 {wiki=comparisons/systems.md overview.md}
- NL4Opt 做第 1、2 站，OptiMUS 做第 1～4 站，Chain-of-Experts 做第 2～4 站，OptiGuide 做第 3～5 站，OPRO 不走這五站。
- OptiMUS 的代表數字：解出的題目接近基本提示的兩倍。版本差異：v1 摘要寫多解出 67%，v2 摘要寫接近兩倍，內文寫提高 91%。
- 做系統時可以從不同來源借每一站的做法；各系統的數字來自不同考卷與 LLM，不能拿來比誰比較強。

## K23 另一條研究路線：訓練 LLM 本身更會建模 {wiki=topics/training-and-data.md}
- 三種做法：**資料合成**（自動產生更多「題目＋模型」的練習資料）、**監督式微調**（用這些資料再訓練 LLM）、**對齊**（讓模型的輸出更符合偏好）。
- 微調過的 ORLM-LLaMA-3 8B 在 IndustryOR 得到 42.9%、在 ComplexLP 得到 59.5%，在較難的資料集上勝過 Chain-of-Experts。
- 還沒解決的問題：長的推理過程很難標註；針對最佳化建模的訓練技術研究還不夠。

## K24 限制與風險：模型會想錯、數字不一定可信、資料可能外流 {wiki=topics/risks-and-design.md topics/multi-agent.md}
- 模型可能一開始就想錯；題目越複雜，正確率越低；多數基準資料集的錯誤率超過 15%，準確率數字不一定可信。
- 專家意見多了，會超過 LLM 一次能讀的上下文長度；步驟越多，API 呼叫越多。
- 把公司資料直接交給 LLM 有外流風險，OptiGuide 讓資料留在求解器與資料庫。

## K25 設計建議：計算交給求解器、驗證交給程式、保留人的判斷 {wiki=topics/risks-and-design.md}
- 計算交給求解器，不讓 LLM 心算；驗證交給不是 LLM 的程式；錯了要帶著錯誤訊息重做。
- 設定重試上限、能停下來回報、保留人的判斷，並用可靠的題目評估。
- 本專案產生簡報的 Loop 就是照這些設計建議設計的：產生者和驗證者分開、驗證不過要附問題清單、每一步都有重做次數上限、關鍵處停下來給人確認。
