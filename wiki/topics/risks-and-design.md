# 限制、風險與設計建議

把所有來源提到的問題，整理成「做一個 LLM × OR 系統時要注意什麼」。

## 限制與風險

1. **模型可能一開始就想錯。** 驗證回圈只修得了小錯，修不了根本的建模錯誤 [S3]。
2. **題目越複雜，正確率越低。** Chain-of-Experts 用 GPT-4 時，基礎題 64.2%、複雜題 31.4% [S4]。
3. **準確率數字不一定可信。** 多數基準資料集的錯誤率超過 15% [S1]，題目也可能早就在訓練資料裡 [S3]。
4. **長度、時間與費用。** 專家意見多了會超過上下文長度，步驟越多 API 呼叫越多 [S4]；大問題也放不進提示 [S5]。
5. **資料安全。** 把公司資料直接交給 LLM 有外流風險，OptiGuide 的做法是讓資料留在求解器與資料庫 [S6]。

## 設計建議（每一點都對應來源的做法）

| 建議 | 來源的做法 |
| --- | --- |
| 計算交給求解器，不讓 LLM 心算 | OptiMUS、Chain-of-Experts、OptiGuide 都由求解器計算 [S3][S4][S6]；OPRO 作者也說它不是要贏過求解器 [S5] |
| 驗證交給不是 LLM 的程式 | Chain-of-Experts 的評估器不是 LLM [S4]；弱的 LLM 自己產生的測試常常誤導 [S3] |
| 錯了要帶著錯誤訊息重做 | OptiMUS 把執行錯誤與沒通過的測試交回 LLM [S3] |
| 設定重試上限 | Chain-of-Experts 重複到通過或達到最多次數 [S4]；OptiMUS 多做一兩次後就不太再提升 [S3] |
| 能停下來回報 | OptiGuide 的 Safeguard 可以停止並回報錯誤 [S6] |
| 保留人的判斷 | 綜述認為系統要能判斷何時需要人介入 [S1] |
| 用可靠的題目評估 | 先檢查考卷，再比較數字 [S1]，見[怎麼評估一個系統](evaluation.md) |

## 和本專案的關係

本專案產生簡報的 Loop，就是照這張表設計的：產生者和驗證者分開、驗證不過要附問題清單、每一步都有重做次數上限、關鍵處停下來給人確認。詳見 [loop/LOOP.md](../../loop/LOOP.md)。
