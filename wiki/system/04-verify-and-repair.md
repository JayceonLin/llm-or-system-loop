# 第 4 站 驗證與修正：試、檢查、再改

## 這一站要做什麼

LLM 第一次寫出的模型或程式常常有錯。這一站把程式真的執行一次、檢查結果，發現錯誤就把錯誤訊息交回給 LLM 修改，重複到通過或達到次數上限。

## 四種做法

| 系統 | 怎麼檢查 | 錯了怎麼辦 |
| --- | --- | --- |
| OptiMUS | LLM 自己產生單元測試，檢查輸出格式、限制是否滿足、結果是否自相矛盾 [S3] | 把執行錯誤與沒通過的測試回饋給 LLM 修正；也會把題目換句話說多跑幾次，任一版本成功就算解出 [S3] |
| Chain-of-Experts | 評估器執行程式與測試案例，評估器本身不是 LLM [S4] | 反向反思：把專家倒過來逐一檢查，找出並修正錯誤，重複到通過或達到最多次數 [S4] |
| OptiGuide | Safeguard 檢查 LLM 產生的程式 [S6] | 觸發自我除錯，或停下來回報錯誤 [S6] |
| OPRO | 計算每個候選解的分數 [S5] | 把解和分數放回提示，請 LLM 提出更好的解 [S5] |

## 這個回圈的極限

- **只修得了小錯：** 漏掉限制式、語法錯誤修得好；根本的建模錯誤修不了 [S3]。
- **卡住就出不來：** 一旦卡在錯誤的解空間，再多試幾次也很少有用 [S3]。
- **檢查本身可能是錯的：** 用 GPT-3.5 時，自動產生的測試常常誤導，反而降低表現 [S3]。
- **很快就沒有進步：** 多做一兩次改寫或除錯後，效果就不太再提升 [S3]。

## 設計這一站時可以學的

- 讓不是 LLM 的程式來執行與判斷，例如 Chain-of-Experts 的評估器 [S4]。
- 設定最多重試次數，Chain-of-Experts 就是重複到通過或達到上限為止 [S4]。
- 讓系統可以停下來回報，而不是無限重試，例如 OptiGuide 的 Safeguard [S6]。

更多設計建議見[限制、風險與設計建議](../topics/risks-and-design.md)。
